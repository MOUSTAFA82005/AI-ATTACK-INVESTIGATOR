How it works

From one log file to a decision

Six steps run on every upload. Each one is a separate model or rule set you can inspect.

  1. Read the log

    Nginx and Apache combined, JSON lines, IIS and W3C. Request bodies are used when the log has them.

  2. Score every request

    An XGBoost detector looks at the values a visitor sent, not at site-specific words, so it works on sites it never saw.

  3. Follow each visitor

    Requests are grouped by address and browser. A behaviour model spots brute force, scanning and ID enumeration.

  4. Name the attack and its stage

    SQL injection, XSS, traversal, command injection and more, placed on recon, intrusion, exploitation or data theft.

  5. Decide what to do

    Block, rate limit or allow, with ready ModSecurity and Nginx rules for the exact pages that were hit.

  6. Show how to fix it

    The nearest OWASP and CWE entries, with the concrete code changes that close the hole.

Under the hood

Eight models, one case file

Each box is a separate model, trained and tested on its own. The output of one is the input of the next.

  1. InputAccess logany site

Security

A security tool that is secure itself

Logs hold addresses, sessions and sometimes passwords. The dashboard is locked down like the systems it protects.

  • Two-step loginPassword, then a 6-digit code sent to your e-mail. Each code works once and ends in 10 minutes.
  • Confirmed e-mailPick a user name and add your e-mail; a code proves the address is yours before the account works.
  • Passwords never storedOnly a salted scrypt hash. Five wrong tries lock the address for a minute.
  • Private resultsEvery saved investigation belongs to one user. Nobody else can open it.
  • Attack payloads stay textLog content is never run as code in the browser, and the page allows scripts from this server only.
  • Logs stay on your machineNo cloud upload, no outside fonts or scripts. It works offline.
Honest limits

What it does not do well yet

Every result above has a known edge. These are the ones a reviewer should ask about.

  • Quiet ID enumerationAn attacker reading other users' records one ID at a time, with normal-looking answers, is often missed.
  • XSS hunting toolsTools that mostly send harmless marker strings are caught far less than classic payloads.
  • The next-step guessLearned from lab attacks; there was not enough real multi-step attacker data to measure it.
  • Shared addressesUsers behind one proxy or NAT can share a visitor, so one attacker can affect others on that address.
FAQ

Questions we get asked

Does it only work on the sites it was trained on?

No. The detector reads the shape of the values a visitor sends, not words from one site. It was tested on sites it never saw, and the results above include two of them.

Is it just a list of rules?

No. Detection, behaviour, attack type and stage are learned models. A rules-only baseline is kept next to every result so you can see what the models add, and where rules still win.

Which log formats can I upload?

Nginx and Apache combined, JSON lines, IIS and W3C. If the log has request bodies, they are used too.

Does my log leave my computer?

No. Everything runs on the machine that hosts the dashboard. There are no outside scripts, fonts or trackers.

How was it tested fairly?

The test logs were sealed by hash before training, the decision rule was written down first, and the frozen models were run on them once. Nothing was tuned after.
